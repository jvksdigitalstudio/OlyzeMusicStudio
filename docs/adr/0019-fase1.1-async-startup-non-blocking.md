# ADR 0019 — Fase 1.1 §15: `AppServices.start()` deja de bloquear el hilo llamador

**Estado:** RESUELTO (con las salvedades de ejecución de tests que se
detallan abajo).

## Contexto

Continuación de ADR 0016/0017/0018. Confirmado por lectura del código
real: `MainViewModel.init { services.start() }` corre en el hilo que
construye el ViewModel — en el flujo real de Android
(`viewModels()`/`ViewModelProvider` desde `MainActivity.onCreate()`), eso
es el hilo principal. `AppServices.start()` (antes de este fix) llamaba
a `audio.start(profile)` de forma completamente síncrona —
`AudioCommandDispatcher.dispatchBlocking()` internamente hace
`executor.submit(Callable { block() }).get()`, bloqueando al llamador
hasta que el motor nativo termina `openStream()` → construcción del DSP
graph → `requestStart()`. En cada arranque de la app, esto bloqueaba el
hilo principal durante toda la negociación real con el HAL de audio de
Android — el defecto exacto que describe la sección 15 del prompt de
Fase 1.1.

## Bug secundario encontrado de paso (no buscado, mereció fix igual)

Auditando esta ruta se encontró que el código anterior llamaba a
`midi.registerConsumer(midiToSynth.consumer)` y `midi.start()`
**incondicionalmente**, sin mirar el `Boolean` que `audio.start(profile)`
devuelve — es decir, si el motor de audio fallaba al arrancar, la MIDI
Foundation se registraba y arrancaba de todas formas, dejando el sistema
en un estado inconsistente (MIDI activo, audio no). Corregido como parte
de este mismo cambio: `midi.registerConsumer()`/`midi.start()` ahora solo
corren en la rama `true` del resultado.

## Decisión de diseño

- **`EngineInitState`** (nuevo, `sealed interface`): `NotStarted` /
  `Starting` / `Ready` / `Failed(reason)`. Expuesto como
  `AppServices.initState: StateFlow<EngineInitState>` y reexpuesto en
  `MainViewModel.engineInitState` para que la UI pueda observarlo sin
  bloquear nada.
- **`start()` ya no bloquea.** Lanza el trabajo real en `scope` (el
  `CoroutineScope` que `AppServices` ya poseía y ya cancelaba en
  `shutdown()` — no una corrutina nueva sin dueño) y publica el progreso
  en `initState`.
- **Ownership explícito**: `startJob: Job?` — es lo que permite que
  `shutdown()` sepa exactamente qué cancelar. El prompt de origen prohíbe
  explícitamente "esconder el problema con simplemente lanzar otra
  coroutine sin definir ownership"; este campo es la respuesta directa a
  esa prohibición.
- **Timeout**: `withTimeoutOrNull(kStartTimeoutMs = 5_000L)`. Documentado
  como valor de partida razonable, no una medición del percentil 99 real
  de ningún dispositivo — no hay forma de medir eso en este entorno.
- **Cancelación — límite honesto, no idealizado.** `runInterruptible
  (Dispatchers.IO) { audio.start(profile) }` — aprovecha que
  `AudioCommandDispatcher.dispatchBlocking()` YA capturaba
  `InterruptedException` explícitamente (para el caso de cierre
  concurrente, ver ADR 0014/0015), así que cancelar `startJob` interrumpe
  al hilo que espera el `Future.get()` y esta corrutina deja de esperar
  de inmediato. Documentado explícitamente en el código lo que esto NO
  garantiza: la llamada nativa `delegate.start(profile)`, que ya fue
  encolada en el hilo único `eliner-audio-commands`, sigue ejecutándose
  hasta terminar — interrumpir al que espera no cancela el trabajo que ya
  se entregó a otro hilo. Esto es seguro de todas formas porque
  `stop()`/`close()` posteriores (en `shutdown()`) se encolan en el MISMO
  `AudioCommandDispatcher` y se ejecutan DESPUÉS por el contrato FIFO ya
  verificado en ADR 0014/0015 — no se inventó ninguna garantía nueva para
  sostener esto, se reutilizó una que ya existía.
- **`shutdown()` cancela, no espera (`join`)** el `startJob` en vuelo —
  esperar reintroduciría el mismo bloqueo del hilo llamador que esta
  sección existe para eliminar (`shutdown()` se llama desde
  `MainViewModel.onCleared()`, también en el hilo principal).

## Tests

### `test_engine_init_state_machine_model.cpp` (nuevo, réplica en C++ puro)

**Alcance honesto, explicado en el propio archivo**: a diferencia de
ADR 0016/0017/0018, esta sección depende de maquinaria real de
`kotlinx.coroutines` (`withTimeoutOrNull`, `runInterruptible`,
`Dispatchers.IO`) que no tiene sentido reimplementar en C++ — esa parte
ya está probada por JetBrains, no es lógica de negocio de Olyze. Lo que
SÍ es lógica propia de esta clase, y lo que este test aísla, es la
máquina de estados en sí y la propiedad de "punto de no retorno": una vez
que `shutdown()` cancela, el camino de éxito (registrar MIDI, publicar
`Ready`) nunca se ejecuta, sin importar el resultado real ni el orden
exacto de la carrera.

5 casos, incluyendo un **Caso 5 con hilos reales** (20 000 ejecuciones de
la carrera `completeStart()` vs. `shutdown()` con dos `std::thread`
reales, no simulada) verificando dos invariantes: el consumer MIDI nunca
se registra más de una vez, y nunca se llega a `Ready` si la cancelación
ya surtió efecto en el momento del último chequeo interno.

**EJECUTADO: SÍ, dos veces con sanitizers distintos** (ASan+UBSan no son
compatibles con TSan en la misma compilación — se corrió cada
combinación por separado):
- `g++ -fsanitize=address,undefined` → PASS, 0 fallos, 0 reportes.
- `g++ -fsanitize=thread` (relevante aquí porque el Caso 5 sí usa hilos
  reales, a diferencia de los tests anteriores de esta fase) → PASS, 0
  fallos, **0 data races detectadas** en 20 000 ejecuciones concurrentes.

### `AppServicesStartupTest.kt`

Se **descartó** deliberadamente escribir este archivo con contenido real:
`AppServices` requiere un `android.app.Application` real (contexto de
instrumentación), así que un test JVM puro contra la clase real no es
posible sin un doble de `Application`/`Context` completo — y un test con
solo un `assertTrue(true)` de relleno sería exactamente el tipo de
"prueba placeholder sin valor" que el prompt de esta fase prohíbe
explícitamente ("no aceptar un test que solamente contenga [SKIP]").
Se documenta aquí, en el ADR, en vez de fingir cobertura: la verificación
end-to-end real de `AppServices.start()`/`shutdown()` contra la clase
real necesita un test instrumentado (`androidTest`, con
`ApplicationProvider.getApplicationContext()`), no ejecutable en este
entorno de todas formas. Queda como follow-up explícito para el usuario,
en un entorno con Gradle/emulador real.

## Compatibilidad con código existente

`MainViewModel.init { services.start() }` se mantiene igual en la
llamada (la firma de `start()` no cambió, sigue siendo `fun start()`
sin retorno) — el cambio de comportamiento es interno (ya no bloquea) y
aditivo (nuevo `engineInitState` observable). Ningún consumidor existente
de `AppServices`/`MainViewModel` se rompe por este cambio.

## Veredicto de esta sesión (§15 específicamente)

RESUELTO — arranque ya no bloquea el hilo llamador, estado observable
real, timeout, ownership explícito del job, cancelación con límites
documentados honestamente (no una promesa de abort nativo que no se
puede sostener), y un bug secundario real corregido de paso (MIDI
arrancaba sin importar si el audio lo hizo). Máquina de estados
verificada por ejecución real con ASan+UBSan y por separado con TSan
(hilos reales). Test Kotlin de integración descartado por ser inviable
sin instrumentación — documentado como tal, no fingido.

Con esto quedan cerradas §16 (ADR 0016), §18 (ADR 0017), §14 (ADR 0018) y
§15 (este documento). Siguen sin auditar, y se mantienen anotadas como
tales: §17 (MIDI channel end-to-end), §19-22 (ThreadManager, frontera de
API de EliNer, posible duplicación de arquitecturas de audio, parameter
system). No se declara la Fase 1.1 completa.
