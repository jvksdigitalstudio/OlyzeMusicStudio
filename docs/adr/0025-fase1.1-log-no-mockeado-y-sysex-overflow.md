# ADR 0025 — Dos bugs reales encontrados por la primera ejecución real de los tests Kotlin (91 tests, 8 fallos)

**Estado:** ambos corregidos. Este documento existe porque el usuario
ejecutó, por primera vez en la historia de este proyecto, los 91 tests
Kotlin en CI real — algo que ningún entorno de desarrollo de esta fase
pudo hacer por sí mismo. Es la tercera vez que una ejecución real de CI
encuentra algo que la verificación de este entorno no podía (ver ADR 0021
#9-10) — funcionando exactamente como la red de seguridad que se pidió.

## Bug 1 — `android.util.Log` no mockeado hace fallar 7 de los 8 tests de `AudioCommandDispatcherTest`

### Diagnóstico

Los 7 tests fallidos de `AudioCommandDispatcherTest` (`close is idempotent`,
`commands after close never throw` ×2, `close prevents further commands`,
`shutdown race`, `concurrent UI and MIDI producers`, y uno más) fallaban con
`java.lang.RuntimeException`, no `AssertionError` — señal de que algo
lanzaba una excepción real, no que una aserción fallara.

Causa: `AudioCommandDispatcher.kt` llama a `android.util.Log.w`/`.e` en sus
rutas de rechazo (post-`close()`, cola llena). En un test JVM puro
(`testDebugUnitTest`, sin Robolectric/instrumentación — la política
explícita y documentada de este módulo, "Core testeable sin Android"), el
`android.jar` de test que provee el AGP tiene TODOS los métodos de
`android.util.Log` con cuerpo `throw new RuntimeException("Method ... not
mocked. ...")`. Cualquier llamada real a `Log.w()`/`Log.e()` lanza esa
excepción — no es un bug de `AudioCommandDispatcher` en sí.

**Esto NO es un bug que yo introduje.** `import android.util.Log` y las 4
llamadas a `Log.w`/`Log.e` ya existían en el `AudioCommandDispatcher.kt`
ORIGINAL, de antes de cualquier cambio de esta fase (Fase 1,
ADR 0014/0015) — verificado contra el zip original del usuario. Lo que SÍ
hizo esta fase (ADR 0018, cola acotada) fue: (a) añadir más rutas de código
que llaman a `Log` (`submitOrdered`), y (b) introducir por primera vez un
escenario de rechazo por CAPACIDAD (antes solo existía rechazo por
`close()`) — eso es lo que hace que el test "concurrent UI and MIDI
producers" (que nunca llama a `close()` durante la carga) también dispare
la ruta de `Log` bajo la carga concurrente de ese test. Pero la causa raíz
— `Log` sin mockear — es preexistente y llevaba latente desde Fase 1,
invisible porque ningún test se había ejecutado nunca hasta que el usuario
corrió el CI real.

### Fix

`eliner/build.gradle.kts`, bloque `android { testOptions { unitTests {
isReturnDefaultValues = true } } }` — la solución oficial de Android para
exactamente este caso (documentación del AGP, "Unit tests that require
Android framework APIs"), no un atajo ni un `try/catch` para esconder el
problema. Con esto, `Log.w()`/`Log.e()` devuelven `0` (valor por defecto)
en vez de lanzar, durante los tests únicamente — el comportamiento en
producción (donde `android.util.Log` es la implementación real del
sistema) no cambia en absoluto.

Se evaluó explícitamente la alternativa de introducir una abstracción de
logging propia (el proyecto ya tiene `com.yeivikas.olyze.eliner.diagnostics.
Logger`, separado en ADR 0022) inyectada en `AudioCommandDispatcher` en vez
de usar `android.util.Log` directamente — más "puro" arquitectónicamente,
pero un refactor mucho más invasivo (cambia la firma del constructor, el
único sitio de construcción, y el patrón ya establecido en
`EliNerAudioBridge.kt`, que tiene el mismo `Log` directo) para resolver un
problema que la propia Google ya resuelve con una línea de configuración
estándar. Se descartó por desproporcionado frente al problema real.

### Por qué solo `:eliner` y no `:app`

`grep` confirmó `android.util.Log` usado únicamente en 2 archivos de
`:eliner` (`AudioCommandDispatcher.kt`, `EliNerAudioBridge.kt`) y ninguno en
`:app`; `:app` tampoco tiene tests unitarios propios (`app/src/test` no
existe). `testOptions` se añadió solo a `eliner/build.gradle.kts`.

## Bug 2 — SysEx sobredimensionado se emitía TRUNCADO, no descartado entero

### Diagnóstico

`MidiStreamParserTest > sysex - oversized payload is dropped entirely, not
truncated` fallaba con `AssertionError` — real, no relacionado con `Log`.

`MidiStreamParser.kt` acumula los bytes de un SysEx en `sysexBuffer`, con
un tope: `if (sysexBuffer.size < MAX_SYSEX_BYTES) sysexBuffer.add(...)` —
bytes más allá del tope se descartan de la acumulación, pero **el código no
registraba que eso había pasado**. Al cerrar el SysEx (`0xF7`), la condición
para decidir si emitir el evento era `sysexBuffer.size <= MAX_SYSEX_BYTES`
— pero como la acumulación de arriba YA garantiza que `sysexBuffer.size`
nunca puede superar `MAX_SYSEX_BYTES`, esa condición es una **tautología**:
siempre verdadera, sin importar cuántos bytes reales tuviera el mensaje. El
resultado real: un SysEx de, por ejemplo, 5000 bytes (`MAX_SYSEX_BYTES` =
4096) no se descartaba — se emitía iguaL, **truncado silenciosamente a
4096 bytes**, exactamente el comportamiento que el propio comentario del
código decía evitar ("Oversized SysEx is silently dropped, not delivered
partially"). Un bug real y preexistente, no relacionado con ningún cambio
de esta fase — `MidiStreamParser.kt` nunca se había tocado hasta ahora.

Un SysEx truncado emitido como si fuera completo es potencialmente peor que
descartarlo: un consumidor (p. ej. un futuro receptor de bulk dump / patch
data) podría interpretar datos incompletos como válidos.

### Fix

Se separó la señal de "hubo overflow" (`sysexOverflowed: Boolean`) del
tamaño del buffer — se marca exactamente en el punto donde un byte real se
descarta por exceder el tope, y se resetea al iniciar cada SysEx nuevo (no
se filtra de un mensaje al siguiente — verificado explícitamente en el
Caso 5 del test). La condición de emisión pasa a ser `if (!sysexOverflowed)`
en vez de comparar tamaños.

## Tests

### `test_midi_sysex_overflow_model.cpp` (nuevo) — EJECUTADO
Réplica en C++ puro de AMBAS versiones (`OldSysexHandler`/`NewSysexHandler`)
en el mismo archivo — no solo prueba el fix, PRUEBA EL BUG: el Caso 2
confirma que el código viejo emite igual (truncado) para un payload que
excede el límite, y que el código nuevo lo descarta entero. Incluye el caso
límite exacto (`kMax+1` bytes, Caso 4), el borde no-overflow (`kMax` bytes
exactos, Caso 3) y que el estado de overflow no se filtra entre mensajes
consecutivos (Caso 5). `g++ -fsanitize=address,undefined` → **PASS, 0
fallos, 0 reportes.**

### Regresión
`run_native_tests.sh`: 22 ejecuciones (incluye el test nuevo), 0 problemas.
La réplica C++ de canal MIDI de ADR 0020 (`test_midi_stream_parser_channel_
model.cpp`) NO implementaba el tope de tamaño de SysEx en absoluto (alcance
deliberadamente distinto, solo canal) — no heredaba este bug, verificado
por lectura, no se necesitó tocarla.

### `AudioCommandDispatcherTest.kt`/`MidiStreamParserTest.kt`
Tests YA EXISTENTES (no nuevos de esta sesión) — su próxima ejecución real
en CI (tras este fix) es la verificación pendiente. No se modificó ningún
test existente para este ADR: ambos bugs eran del código de producción, no
de los tests, que ya estaban escribiendo la especificación correcta.

## Auditoría adicional realizada en esta sesión

Antes de escribir el fix, se verificó exhaustivamente que ni `EliNerCore.kt`
(el archivo del bug de ADR 0024) ni `eliner/build.gradle.kts` quedaran con
problemas estructurales tras los cambios: balance de llaves/paréntesis
(ambos limpios) y un detector de declaraciones duplicadas de constructor/
miembro de clase aplicado a `MidiStreamParser.kt` (0 duplicados).

## Veredicto

Ambos bugs corregidos y verificados por ejecución real (C++, con
demostración explícita del bug además del fix). Pendiente, como en cada ADR
de esta fase: que el usuario vuelva a correr el CI real — es la única
verificación de `kotlinc`/`testDebugUnitTest` que este entorno no puede
hacer por sí mismo. Si los 91 tests pasan esta vez, el siguiente paso real
sería `Build Debug APK`, la primera confirmación de que el proyecto
completo compila y empaqueta de punta a punta tras las cinco sesiones de
esta fase.
