# ADR 0026 — Tres fallos reales de test: carreras de sincronización preexistentes + un volumen incompatible con la cola acotada de §14

**Estado:** corregidos los tres. Cuarta vez que una ejecución real de CI
encuentra algo que este entorno no podía (ver ADR 0021 #9-10, ADR 0025) —
de 8 fallos a 3, y estos tres ya eran `AssertionError` genuinos, no el
`RuntimeException` de `Log` (ya resuelto en ADR 0025).

## Contexto

Con el fix de ADR 0025 (`isReturnDefaultValues = true`) aplicado, los 91
tests corrieron sin que `android.util.Log` interrumpiera nada — pero 3
tests de `AudioCommandDispatcherTest.kt` siguieron fallando, esta vez con
`AssertionError` real: fallos de lógica, no de infraestructura de test.

## Corrección a una afirmación anterior

ADR 0018 (§14, cola acotada) afirmó: "Se revisó `AudioCommandDispatcherTest.
kt` línea por línea... No se requirió modificar ningún test existente."
**Esa afirmación era incorrecta** — confirmado ahora por ejecución real,
no por otra lectura manual. Uno de los tres fallos (`concurrent UI and MIDI
producers`) es precisamente el caso que esa revisión no detectó: su
volumen (2 × 500 = 1000 comandos) excede la capacidad de la cola acotada
(256, ADR 0018) que la propia sección introdujo a propósito. Se documenta
aquí, no se oculta.

## Causa raíz común de dos de los tres — una carrera de sincronización preexistente, no introducida por esta fase

`insertModule and getModuleType preserve FIFO order relative to note
events` y `close prevents further commands from reaching the delegate`
comparten el mismo defecto: ambos llaman a un método *fire-and-forget*
(`noteOff`/`noteOn` — `dispatchAsync`, que NO espera a que el comando se
ejecute, solo a que quede encolado) y, inmediatamente después, sin ninguna
barrera de sincronización, leen `fake.callLog` — con una carrera real entre
"el hilo único del dispatcher ya procesó esto" y "el test ya está leyendo
el resultado".

Esto **no lo introdujo ninguna sesión de esta fase** — es un defecto de
diseño del propio archivo de test, que existía desde que se escribió
(Fase 1, ADR 0014/0015) y que ninguna ejecución real había podido exponer
hasta ahora, porque **ningún test de este proyecto se había ejecutado
nunca** antes de que esta fase añadiera el paso de CI correspondiente (ADR
0023). Es exactamente el tipo de hallazgo que una ejecución real revela y
que ninguna lectura de código, por cuidadosa que sea, puede garantizar
capturar.

### Fix — `flush()`, una barrera de sincronización determinista

Se añadió un helper privado a la clase de test:

```kotlin
private fun AudioCommandDispatcher.flush(slot: Int = 0) {
    getModuleType(slot)
}
```

`getModuleType()` es una llamada BLOQUEANTE (`dispatchBlocking`,
`executor.submit(...).get()`). En un executor de un único hilo con entrega
FIFO (el invariante central de esta clase, verificado en ADR 0014/0015),
cuando esta llamada retorna, el hilo dispatcher ya procesó absolutamente
todo lo que se había encolado ANTES que ella — incluida cualquier llamada
fire-and-forget previa. No es un `Thread.sleep` disfrazado: es una
garantía real del propio diseño FIFO de la clase bajo prueba, no una
suposición de timing.

Se insertó `dispatcher.flush()` en los dos tests, en el punto exacto donde
antes había una lectura racy de `callLog`, y se actualizaron las
aserciones para dar cuenta de la entrada adicional que `flush()` añade a
`callLog` (es honesto: no se oculta que la barrera también queda
registrada).

## Causa del tercer fallo — volumen incompatible con la cola acotada de §14 (deliberada, no un bug)

`concurrent UI and MIDI producers are all executed on a single physical
thread` enviaba 500 comandos por productor (1000 en total) contra una cola
acotada a 256 (ADR 0018) — bajo esa carga, una parte real puede
descartarse POR DISEÑO (backpressure real, el objetivo explícito de §14).
La aserción original ("no debe perderse ni duplicarse ningún comando")
medía exactamente lo que §14 dejó de garantizar a propósito para volúmenes
que exceden la capacidad.

### Fix

`eventsPerProducer` reducido de 500 a 50 (100 total + 2 barreras = 102,
muy por debajo de 256) — preserva la intención original del test (verificar
ejecución en un único hilo físico + ausencia de pérdidas/duplicados) bajo
carga NORMAL, sin contradecir el backpressure real que §14 introdujo para
carga QUE EXCEDE la capacidad. También se le añadió `flush()` antes de leer
el tamaño final de `callLog`, por el mismo motivo que los otros dos tests.

Se documenta explícitamente, en el propio test, que esto NO sustituye una
verificación de backpressure bajo sobrecarga real — esa cobertura ya existe
a nivel de mecanismo en `test_dispatcher_coalescing_and_backpressure_model.
cpp` (C++, ADR 0018) para el caso de parámetros coalescibles; una prueba
Kotlin determinista de backpressure para EVENTOS DISCRETOS bajo sobrecarga
real queda como follow-up explícito, no fabricada aquí sin poder
ejecutarla.

## Auditoría del resto del archivo

Revisados los 5 tests restantes de `AudioCommandDispatcherTest.kt`
(`start returns...`, `commands after close...` ×2, `close is idempotent...`,
`shutdown race...`) uno por uno contra el mismo patrón de carrera — ninguno
lo tiene: o bien `close()` ocurre ANTES de cualquier comando (rechazo
síncrono garantizado, sin ventana de carrera), o bien la aserción es sobre
una propiedad que no depende de sincronización externa (`accepted.get() ==
attempts`, un límite superior `callLog.size <= attempts`). Consistente con
que ninguno de los cinco apareció en la lista de fallos real de CI.

## Verificación

- Balance de llaves/paréntesis de `AudioCommandDispatcherTest.kt`: limpio.
- Suite C++ (`run_native_tests.sh`): 22 ejecuciones, 0 problemas — este
  cambio es puramente Kotlin, la regresión confirma que no se tocó nada
  del lado nativo.
- **No ejecutado con `kotlinc`/Gradle real en este entorno** — mismo
  disclaimer que cada ADR de esta fase. Es exactamente lo que el usuario
  está verificando en CI real, turno a turno.

## Veredicto

Tres fallos corregidos con causa raíz identificada y documentada para cada
uno — dos carreras de sincronización preexistentes (no introducidas por
esta fase, expuestas por la primera ejecución real del archivo) y un
volumen de test genuinamente incompatible con el backpressure deliberado
de §14 (corrección a una afirmación previa de ADR 0018, ahora explícita).
Pendiente, como siempre en esta fase: la próxima ejecución real de CI. Si
los 91 tests pasan esta vez, el flujo avanza a `Build Debug APK` por
primera vez.
