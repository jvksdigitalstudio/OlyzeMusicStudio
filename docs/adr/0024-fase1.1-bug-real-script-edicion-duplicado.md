# ADR 0024 — Bug real de compilación introducido por mi propio script de edición, encontrado por la primera ejecución real de `kotlinc` en CI

**Estado:** corregido. Este documento existe para ser honesto sobre una
limitación real de método, no para minimizarla.

## Qué pasó

En la sesión de ADR 0022 (§19/§20 — frontera de la API pública), al hacer que
`EliNerCore` implementara la nueva interfaz `ModuleRegistryContract`, usé un
script de Python con `str.replace()` para insertar `: ModuleRegistryContract`
en la declaración de la clase. El patrón de búsqueda de ese `replace()` no
incluía la línea `private val engineName: String = ...` que ya existía justo
antes del punto de inserción — el texto de reemplazo la reintrodujo, dejando
`EliNerCore` con la misma propiedad declarada DOS VECES en su constructor
primario:

```kotlin
class EliNerCore(
    private val engineName: String = EngineVersion.CURRENT.name,
private val engineName: String = EngineVersion.CURRENT.name,   // duplicado, insertado por error
) : ModuleRegistryContract {
```

Esto es un error de compilación real en Kotlin (`Conflicting declarations`),
no un problema de estilo. Con dos `engineName` declarados, cualquier uso de
`engineName` en el cuerpo de la clase (`EngineVersion.CURRENT.copy(name =
engineName)`, línea ~68) se vuelve ambiguo — exactamente los tres errores que
reportó `kotlinc` en la primera ejecución real: dos "Conflicting
declarations" y un "Overload resolution ambiguity" en cascada del mismo
origen.

## Por qué mi propia verificación no lo detectó antes

En cada sesión de esta fase (ADR 0016 en adelante) usé un verificador propio
de balance de llaves/paréntesis/comentarios tras cada edición de un `.kt`,
precisamente para detectar el tipo de daño estructural que un `str.replace()`
descuidado puede causar. Ese verificador SÍ habría detectado paréntesis o
llaves desbalanceadas — pero una declaración duplicada no desbalancea nada:
el archivo seguía siendo sintácticamente bien formado línea por línea, solo
semánticamente inválido (dos símbolos con el mismo nombre en el mismo scope).
Eso es exactamente lo que un compilador real detecta y un chequeo de balance
de delimitadores no puede.

Este entorno no tiene `kotlinc` — lo he dicho honestamente en cada ADR de
esta fase ("test Kotlin escrito, NO ejecutado aquí"), pero el mismo límite
aplicaba también a los cambios de PRODUCCIÓN, no solo a los tests: edité
Kotlin real sin poder compilarlo yo mismo, y el checker de balance que usé
como sustituto parcial tiene este punto ciego real, ahora confirmado.

## Qué hice al enterarme (esta sesión)

1. Corregido el archivo: eliminada la línea duplicada.
2. **No asumí que era el único caso.** Escribí un script que recorre los 20
   archivos `.kt` modificados en TODA la Fase 1.1 (no solo el de ADR 0022) y
   busca líneas de código no-comentario idénticas dentro de una ventana de 3
   líneas — el patrón exacto de este bug (una línea reinsertada cerca de
   donde ya estaba). Resultado: el caso real de arriba (ya corregido) y un
   único hallazgo adicional en `DeviceCapabilityManager.kt`, verificado por
   lectura de contexto como falso positivo genuino (dos propiedades
   distintas —`nativeSampleRate` y `nativeFramesPerBuffer`— que
   legítimamente terminan ambas en `?.toIntOrNull()`, no una duplicación).
3. Releído `EliNerCore.kt` completo, no solo el fragmento corregido, para
   confirmar que no queda ningún otro rastro del mismo error de edición.

## Qué NO puedo garantizar todavía

Esta auditoría heurística (líneas idénticas en ventana de 3) detecta el
patrón específico de ESTE bug — una reinserción accidental cerca del
original — pero no es un compilador. No sustituye a `kotlinc` real. La
recomendación honesta, para cualquier cambio futuro de esta envergadura:
ejecutar `./gradlew :eliner:compileDebugKotlin` (más rápido que la suite
completa de tests, y es exactamente el paso que habría atrapado esto en
segundos en vez de en un ciclo completo de CI) antes de dar por buena una
sesión de cambios grandes en Kotlin, o pedírmelo explícitamente cuando el
entorno lo permita.

## Verificación de este fix específico

- Balance de llaves/paréntesis/comentarios de `EliNerCore.kt`: OK (ya lo
  estaba antes también — este checker nunca iba a atrapar este bug en
  particular, ver arriba).
- Lectura completa del archivo corregido: una única declaración de
  `engineName` (línea 49), un único uso (línea 68).
- Barrido de los 20 archivos `.kt` de toda la fase: sin otros casos reales.
- Suite C++ (`run_native_tests.sh`): no afectada por este cambio (es
  puramente Kotlin) — no se re-ejecutó por este fix específico.

## Veredicto

Corregido. Este es el segundo hallazgo real de una ejecución real de CI
(después del bit de ejecución, ADR 0021 #9) — ambos existen precisamente
porque el usuario ejecutó el build real y compartió el error exacto, que es
lo que este entorno no puede hacer por sí mismo. La Fase 1.1 sigue sin
poder declararse cerrada con evidencia de compilación 100% propia; depende,
como se ha dicho en cada ADR de esta fase, de que el usuario la ejecute y
reporte el resultado — que es exactamente lo que está pasando ahora mismo,
y funcionando como red de seguridad real.
